# QUE retriever evaluation

Component level. Only the retriever is under test here: `app.knowledge.hybrid.select_hybrid`.
No answer generation, no tools, no routing.

## Task definition

Given a user question about Quizzer, the retriever must return the guide text that
contains the answer, and little else.

- In scope: product-help questions answered by `knowledge/` guides.
- Out of scope (must abstain, `no_answer=True`): weather, coding, other products.
- Production path measured: dense Chroma + BM25 with document-level RRF, dense-leader pin,
  `top_k=2`, candidate pool 4, dense floor `QUE_RAG_MIN_SCORE=0.28`.
- Unit of truth: the **expected output** (answer text written from the source guide section),
  not the guide id. The id match is kept only as a diagnostic.

## Metrics

One Gemini call per answered question returns all three scores. They are still
reported separately and never averaged. The earlier run used DeepEval's separate
metric classes (about 8 calls per question) and was stopped.

| Metric | Failure mode it catches | Needs |
|---|---|---|
| Contextual recall | required info not retrieved | expected_output |
| Contextual precision | relevant chunks ranked below noise | expected_output |
| Contextual relevancy | noise injected next to relevant text | input only |
| `ExpectedGuideRecallMetric` | diagnostic: labeled guide missing | `expected_doc_ids` |
| Abstention rate | out-of-domain query got guides | `expect_no_answer` |
| Efficiency | injected chars, latency p50/p95, embedding calls | measured |

Each metric is reported on its own. They are never averaged into one number.

## Provisional targets

Frozen after the first judged run on the human-verified set. They are never lowered to pass.

| Metric | Target |
|---|---|
| Contextual recall (mean) | >= 0.90, no in-domain case below 0.5 |
| Contextual precision (mean) | >= 0.75 |
| Contextual relevancy (mean) | >= 0.80 |
| Abstention | 100% |
| Efficiency | no regression in chars or p95 latency vs baseline |

## Golden set rules

- Candidates are generated by DeepEval `Synthesizer` from `knowledge/` chunks
  (`evals/generate_retriever_goldens.py`). The CLI `deepeval generate --method docs`
  cannot take the repo judge or a non-OpenAI embedder, so the Python API is used.
- Seed rows come from `evals/retrieval_cases.json`; expected outputs are added from guide text.
- A row enters the gate only with `human_verified: true`. Synthetic rows are `false` until reviewed.
- Generator model and judge model are currently the same model. This is circular. Treat judge
  scores as relative (before/after) until a different judge is named, and check the judge
  against hand grades (`evals/judge_check.md`).
- Labels are fixed only when the label is wrong. They are never edited to make a metric pass.

## Categories (v2.0.0)

Every row has `category` and `difficulty`. Report each metric per category, never one pooled number.

| Category | What it tests |
|---|---|
| `basic` | Plain single-guide how-to |
| `paraphrase` | Same ask in different words |
| `typo_short_hinglish` | Typos, one-word asks, Hinglish |
| `ambiguous` | Underspecified asks; several guides are acceptable |
| `multi_doc` | Answer needs two or more guides (top-k 3) |
| `confusable` | Near-synonym terms (Monitoring vs Results, LIVE vs Monitoring) |
| `out_of_domain` | Must abstain at the retriever (production also refuses earlier, in routing) |

Rows from `evals/hard_cases.json` carry `origin: "hard"`. Rows with `label_suspect: true` got
"NOT IN GUIDE" from the answer writer, so the label or the query needs a human look. Rows with
`rejected: true` (basic duplicates, weak labels) stay in the file with a `review_note` but never
enter any run.
